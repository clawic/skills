# i18n — Translation, Formats, Timezones

Three separate systems that people bundle together and then debug together by mistake: **translation** of source strings, **localized formatting** of numbers and dates, and **timezone** conversion. They are configured differently and fail differently.

## The Switches

| Setting | Controls | Failure when wrong |
|---|---|---|
| `USE_I18N` | Whether translation and localized formatting happen at all | Everything renders in `LANGUAGE_CODE`, silently |
| `LANGUAGE_CODE` | The default language and the fallback | A missing translation falls back here, never to an error |
| `LANGUAGES` | The list users may switch to | A language with a `.mo` file but no entry here is unreachable |
| `LOCALE_PATHS` | Where project-level `.po`/`.mo` files live | `makemessages` writes somewhere the loader never reads |
| `FORMAT_MODULE_PATH` | Custom date/number formats per locale | Locale formats silently stay at Django's own |
| `USE_TZ` | Aware UTC storage; `True` by default since Django >=5.0 | Naive datetimes, `RuntimeWarning`, drifted comparisons |
| `TIME_ZONE` | The zone the ORM and templates convert to | `__date`/`__year` lookups group by the wrong day |

`USE_L10N` was removed in Django >=5.0; localized formatting now follows `USE_I18N`.

## How Django Picks A Language

`LocaleMiddleware` decides, in this order, and stops at the first hit:

1. The language prefix in the URL, when the pattern is inside `i18n_patterns()`.
2. `_language` in the session (older flow) or the `django_language` cookie (`LANGUAGE_COOKIE_NAME`).
3. The browser's `Accept-Language` header, matched against `LANGUAGES`.
4. `LANGUAGE_CODE`.

- `LocaleMiddleware` goes **after** `SessionMiddleware` and **before** `CommonMiddleware`. Placed wrong, the session lookup sees no session and every user gets the header language.
- `i18n_patterns()` is only valid in the **root** URLConf, and it prefixes every URL it wraps. Anything that must stay unprefixed — webhooks, health checks, the API — belongs outside it.
- The `set_language` view is a POST that writes the cookie and redirects; a GET link that "switches language" is a hand-rolled version that skips the redirect validation.
- `translation.activate(code)` sets the language for the current thread, and it stays set. Anything outside the request cycle — a management command, a task sending a localized email — must activate deliberately and use `translation.override(code)` as a context manager so it restores.

## Marking Strings

```python
from django.utils.translation import gettext_lazy as _, gettext, ngettext, pgettext

class Order(models.Model):
    status = models.CharField(_("status"), max_length=20)     # lazy: evaluated at render

def view(request):
    messages.success(request, gettext("Order placed"))        # eager: evaluated now
```

- **`gettext_lazy` for anything evaluated at import time** — model field labels, form labels, `choices`, `verbose_name`, class attributes. Plain `gettext` at module level freezes the string in whichever language happened to be active during import, which in production is the default one, forever.
- **`gettext` inside the function**, where the request's language is already active. A lazy object concatenated with `+` or passed to `json.dumps()` raises or serializes as a proxy; wrap with `str()` at that boundary.
- `ngettext("%d order", "%d orders", n) % n` for plurals. Languages with three or more plural forms exist, and a hand-written `if n == 1` is wrong in them.
- `pgettext("month name", "May")` disambiguates identical source strings with different meanings — the case a translator cannot resolve from the string alone.
- Do not concatenate translated fragments. `_("Hello") + name` produces word order no translator can fix; use `_("Hello %(name)s") % {"name": name}` and keep named placeholders so translations may reorder them.

## Templates

```django
{% load i18n %}
{% translate "Checkout" %}
{% blocktranslate with total=order.total count n=order.items.count %}
{{ n }} item, {{ total }}{% plural %}{{ n }} items, {{ total }}
{% endblocktranslate %}
```

- `{% blocktranslate %}` accepts **only simple variables** — no filters, no attribute chains with method calls. Compute first with `{% with %}` or `{% blocktranslate with x=obj.thing %}`.
- Its `count` argument plus `{% plural %}` is how plural forms work in templates; without them a translator sees one string and cannot express the language's plural rules.
- `{% load i18n %}` is per file. It is not inherited from a parent template, which is the usual reason a tag "does not exist" in an included fragment.
- `{% get_current_language as LANGUAGE_CODE %}` and `{% get_available_languages as LANGUAGES %}` build a language switcher without hardcoding the list.

## The Message Workflow

```
manage.py makemessages -l es              # scan source → locale/es/LC_MESSAGES/django.po
manage.py makemessages -d djangojs -l es  # separate catalog for JavaScript
# translate the .po
manage.py compilemessages                 # .po → .mo, which is what the loader reads
```

- **Django reads `.mo`, never `.po`.** A perfectly translated `.po` with no `compilemessages` step renders the source strings and raises nothing. Compile in the build, and commit the decision (either the `.mo` files or the build step) so it cannot be forgotten.
- `makemessages` finds only marked strings in files it scans. It ignores anything under `.gitignore`-style exclusions it was told about, and it does not look inside a virtualenv.
- `fuzzy` entries are **not used** at render time. A translation updated by a tool and left fuzzy silently falls back to the source string.
- Third-party apps ship their own catalogs; project-level `LOCALE_PATHS` entries take precedence, which is how you override one string without forking the package.
- Review the `.po` diff like code. An unescaped `%(name)s` typo is a `KeyError` at render time, in one language, on one page.

## Content vs Interface

- gettext translates **source strings written by developers**. It cannot translate rows in the database — a product name entered by an editor is data, not a catalog entry.
- For translatable content, the two shapes are a column per language on the model (simple, denormalizing, fine for two or three languages) or a related translation table keyed by language (scales, adds a join to every read). Pick one per project; mixing them is how a field ends up translated in two places.
- Either way, decide the fallback explicitly: a missing translation should render the default-language value, not an empty string.

## Formats And Timezones

- Date and number rendering follows the active locale when `USE_I18N` is on: `{{ value }}` for a `DecimalField` uses the locale's decimal separator. `{% load l10n %}{% localize off %}` forces the raw form — required around values that feed JavaScript or a form input.
- Forms parse localized input too. A user typing `1.234,56` in a locale with comma decimals validates; the same string fails when localization is off. `localize=True` on a form field opts in per field.
- Templates render aware datetimes in the **currently activated** timezone. `{% load tz %}{% localtime off %}` shows UTC; `{{ value|timezone:"Europe/Madrid" }}` converts one value.
- Per-user timezones: `timezone.activate(user_tz)` in middleware, deactivated afterwards. Activating per template is a leak — the next request on that thread inherits it.
- `timezone.localdate()` is "today" in the active zone; `date.today()` is "today" on the server. In an application with users in several zones those are different days for hours at a time.

## Traps

| Trap | Why it fails | Do instead |
|---|---|---|
| `gettext` at module level | Frozen at import in the default language | `gettext_lazy` |
| `.po` edited, nothing changes | Django reads `.mo` only | `compilemessages` in the build |
| `_("Total: ") + str(n)` | Word order is untranslatable | `_("Total: %(n)s") % {"n": n}` |
| `LocaleMiddleware` before `SessionMiddleware` | The session language is never seen | Session → Locale → Common |
| `i18n_patterns` wrapping the API | Every endpoint gains a language prefix | Keep API and webhooks outside it |
| Translating in a task without `override()` | The worker keeps the last activated language | `with translation.override(user.language):` |
