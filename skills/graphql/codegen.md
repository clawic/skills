# Codegen — Types That Cannot Drift From The Schema

Hand-written types for a GraphQL API are a copy of the schema that nothing keeps in sync. Generation makes the schema the single source and turns a category of runtime bug into a build failure. Two directions, and most projects need both.

Contents: The Two Directions · Schema-First Versus Code-First · Resolver Types · Operation Types · Nullability Mapping · Scalar Mapping · Fragment Types · Keeping It Honest · Enums And Unions · Traps

## The Two Directions

| Direction | Input | Output | Prevents |
|---|---|---|---|
| Server | SDL | Resolver signatures, argument and parent types | A resolver returning a shape the schema does not promise |
| Client | SDL + your documents | Typed result and variable types per operation | A component reading a field the query never selected |

- Both directions need the *same* schema artifact. A client generating against a stale schema dump produces types that compile and fail at runtime; pull the schema from the registry or from a file the server itself emits.
- Generation runs in CI, and CI fails when the committed output differs from a fresh run. Generated files that are only regenerated by whoever remembers are worse than none, because they look authoritative.

## Schema-First Versus Code-First

- **Schema-first**: SDL is the artifact, resolvers are typed from it. The contract is reviewable by people who do not read your server language, which is what makes schema review a real gate. Cost: two places to keep aligned, solved by generation.
- **Code-first**: types are built in code, SDL is emitted. Cannot drift by construction, refactors are a rename. Cost: the contract is only visible after a build, and reviewers read implementation instead of interface.
- Both are correct; mixing them inside one service is not. Recorded in `schema_style`.
- The tiebreaker in practice: if a non-server-engineer reviews schema changes, schema-first. If the schema is large and internal, code-first.
- Code-first still needs an SDL artifact committed to the repository — schema checks, client generation and registry publication all consume SDL (`schema-evolution.md`).

## Resolver Types

- Generated resolver types give you: the parent type as *actually returned by the parent resolver*, typed arguments, the context type, and a return type the schema will accept.
- The parent type is the valuable one. It catches the field that assumes the parent loaded a property nobody loads, which is otherwise a runtime `undefined` behind a nullable field, invisible forever (`resolvers.md`).
- Configure the mapping between schema types and your internal models explicitly: a resolver often returns a database row that is *not* the GraphQL type. Without a mapper configuration, generated types demand you return the full GraphQL shape from the top resolver, which defeats field-level resolution.
- Generation cannot know your default resolvers. A field with no resolver is not type-checked against the parent's shape at all — those are the fields that break on a column rename.

## Operation Types

- Every query, mutation and fragment in client source becomes a typed pair: the variables it requires and the data it returns. Both are derived from the schema, so a field removed server-side becomes a compile error in the client build.
- Typed document nodes (a document object carrying its own result and variable types) remove the last manual step: the hook infers everything from the document with no type parameters to pass by hand.
- The generator validates documents against the schema as a side effect — a fragment spread on the wrong type, an unknown field, a missing required variable all become build failures instead of runtime nulls (`client.md`).
- Generate from the *whole* client source, not per file: fragments compose across files, and only a whole-project pass can resolve them.
- Commit the output or generate in CI before typecheck. Either is fine; deciding neither means the types are whatever the last developer had locally.

## Nullability Mapping

- Every nullable GraphQL field becomes an optional or nullable field in the target language. A schema that is nullable-by-default (SKILL.md rule 2, correctly) produces client types full of null checks — and those null checks are the honest representation of what the server can return.
- Teams react by making fields non-null "to clean up the types". That trades a null check for a nulled parent during the next incident. The right answer is null checks in the client, not promises the server cannot keep.
- List nullability generates four distinct shapes (`schema.md`); the generated type is the fastest way to see which one you actually declared.
- Generated *input* types make required-versus-optional visible at the call site, which is where the input-nullability breaking change shows up first (`schema-evolution.md`).

## Scalar Mapping

- Custom scalars generate as `any`/`unknown` until you map them. Every unmapped scalar is a hole in the type safety you just paid for.
- Map to the type you actually receive after JSON parsing: a `DateTime` scalar arrives as a **string**, not a `Date` object, unless a client-side link parses it. Mapping it to `Date` produces types that lie and code that calls `.getTime()` on a string.
- Where server and client need different mappings for one scalar (server produces a `Date`, client receives a string), the generator's separate input/output mapping is the tool. Using one mapping for both is the usual cause of "the type says Date and it is a string".
- Keep the scalar list short. Every scalar is a mapping in every client (`schema.md`).

## Fragment Types

- Fragment types are what make colocation work: a component's props are typed by *its own* fragment, not by the screen's query, so the component can be reused anywhere the fragment is spread.
- Fragment masking (the Relay model, available as an option in other generators) makes reading an unmasked field a compile error. That is what makes deleting a field safe — the compiler proves nobody else read it.
- Without masking, components read whatever the query happened to fetch, and removing a field from one screen's query breaks a component on another screen at runtime.
- Generated fragment types must be regenerated when a fragment moves files; stale artifacts produce duplicate-fragment-name errors that point at the wrong place.

## Keeping It Honest

- CI step: regenerate, then fail if `git diff` is non-empty. This is the entire enforcement mechanism.
- Pull the schema from the registry, not from a running localhost server — a developer's local schema is not the deployed contract (`schema-evolution.md`).
- Run generation before typecheck and before lint, in that order, or the first failure is a missing import instead of the real one.
- Lint documents as well as generate from them (unused fragments, missing `id` on selections of identifiable types, unnamed operations). An unnamed operation is invisible in production telemetry (`production.md`).
- When the schema is federated, generate clients from the *composed supergraph*, never from one subgraph (`federation.md`).

## Enums And Unions

- Generated enums are the fastest way to see the exhaustive-switch problem: adding a server-side value makes existing exhaustive handling incomplete only after you regenerate — a client running old generated types accepts a value it does not know about at runtime.
- Generate enums as a union of string literals rather than a runtime enum object where the language offers the choice: it keeps the values as data, matches what arrives on the wire, and avoids shipping a runtime object nobody uses.
- Unions generate as discriminated unions keyed on `__typename` — which only works if every selection includes `__typename`. Most generators add it automatically; verify (`schema.md`).
- Always handle the unknown-member case in generated union handling. The server can add a member before your client is redeployed.

## Traps

| Trap | Why it fails | Do instead |
|---|---|---|
| Hand-written response types | A copy of the schema that nothing syncs | Generate from the schema |
| Generating against a local or stale schema | Types compile, runtime disagrees | Pull from the registry or a committed emitted SDL |
| Unmapped custom scalars | Everything is `any` at the boundary you care most about | Map every scalar, separately for input and output |
| Mapping `DateTime` to `Date` on the client | It arrives as a string after JSON parse | Map to string, parse deliberately |
| Making schema fields non-null to simplify generated types | Trades a null check for a nulled parent in production | Keep nullability honest, handle nulls |
| Generated files regenerated only by hand | They look authoritative and are stale | CI regenerates and fails on a diff |
| Generating a client from one subgraph | Missing everything other subgraphs contribute | Generate from the composed supergraph |
| No fragment masking and no discipline | Components read fields they did not declare; deletions break elsewhere | Masking, or a lint rule |
