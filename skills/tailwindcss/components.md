# Components — Reuse Without Losing The Utilities

The same 14 classes in 30 places is a component problem. Solving it with `@apply` trades duplication for a private CSS language nobody can override; solving it with a component keeps the utilities visible and the overrides possible.

## The Decision

| Situation | Answer |
|---|---|
| You control the markup and the framework has components | A component with a variant map |
| You control the markup, no component system (Rails/Django/Go templates) | A partial or template include with the classes inline |
| The markup is generated by something else (CMS, Markdown, a library) | `@apply` in a scoped rule, or `prose` from the typography plugin |
| A one-line pattern used twice | Leave it duplicated; two is not a pattern |
| A pattern that must accept variants and stack with `hover:`/`md:` | `@utility` (v4) or a plugin utility (v3), never `@layer components` |

## The Variant Map

```tsx
import { cva, type VariantProps } from 'class-variance-authority';
import { cn } from '@/lib/utils';

const button = cva(
  'inline-flex items-center justify-center rounded-md font-medium transition-colors ' +
  'focus-visible:outline-hidden focus-visible:ring-2 focus-visible:ring-offset-2 ' +
  'disabled:pointer-events-none disabled:opacity-50',
  {
    variants: {
      intent: {
        primary: 'bg-brand-500 text-white hover:bg-brand-600',
        ghost: 'bg-transparent text-brand-600 hover:bg-brand-50',
        danger: 'bg-red-600 text-white hover:bg-red-700',
      },
      size: { sm: 'h-8 px-3 text-sm', md: 'h-10 px-4', lg: 'h-12 px-6 text-lg' },
    },
    defaultVariants: { intent: 'primary', size: 'md' },
  },
);

export function Button({ intent, size, className, ...props }:
  React.ComponentProps<'button'> & VariantProps<typeof button>) {
  return <button className={cn(button({ intent, size }), className)} {...props} />;
}
```

Three properties this has and `@apply` does not: every class is a literal string the scanner sees, IntelliSense works inside the map, and the trailing `className` lets a caller override without `!important`.

## `cn`, `clsx`, And `tailwind-merge`

```ts
// lib/utils.ts — the standard pair
import { clsx, type ClassValue } from 'clsx';
import { twMerge } from 'tailwind-merge';
export const cn = (...inputs: ClassValue[]) => twMerge(clsx(inputs));
```

- `clsx` handles conditionals and arrays; it does **not** resolve conflicts. `clsx('p-4','p-6')` returns both, and the stylesheet decides — which is why a caller's `p-6` loses to the component's `p-4` at random (SKILL.md rule 3).
- `twMerge` knows the conflict groups and keeps the last: `twMerge('p-4','p-6')` → `'p-6'`. That is what makes `className` a real override slot.
- Custom utilities from your theme are invisible to `twMerge` until you teach it:

```ts
import { extendTailwindMerge } from 'tailwind-merge';
export const twMerge = extendTailwindMerge({
  extend: { classGroups: { 'font-size': [{ text: ['hero', 'display'] }] } },
});
```

Skip this and `cn('text-hero','text-sm')` keeps both, with the sheet order deciding.

- `twMerge` runs on every render. On a list of thousands of rows it shows up in a profile; memoize the class string or drop back to a static string where no override is possible.
- Order matters: the override always goes **last** in `cn(...)`.

## `@apply` — When It Is Right, And How

The legitimate uses are exactly three and the list is closed (SKILL.md rule 2): third-party HTML, `::-webkit-*` pseudo-elements, print sheets. A class API for non-JS templates is **not** on it — Rails, Django, and Go templates get a partial or include with the classes inline, per the decision table above.

```css
@layer components {
  .prose-callout { @apply rounded-md border-l-4 border-brand-500 bg-brand-50 p-4; }
}
```

- `@apply` **does** support variants — `@apply hover:bg-blue-500 md:p-6` compiles. The old claim that it drops them is false; what it costs is discoverability and the ability to override from markup.
- `@apply` only accepts Tailwind-generated classes. Applying a class you wrote yourself fails; extract the declarations or define it with `@utility`.
- In `@layer components`, the rule loses to any utility — which is what you want for a base style. Outside a layer (v4), it beats every utility, which is almost never what you want.
- In a Vue SFC `<style>`, a Svelte `<style>`, or a `.module.css`, v4 needs `@reference "../app.css";` at the top of the block or the build fails with "Cannot apply unknown utility class".

## Custom Utilities That Behave Like Real Ones

```css
/* v4 — sorts with utilities, accepts every variant, works with @apply */
@utility scrollbar-none {
  scrollbar-width: none;
  &::-webkit-scrollbar { display: none; }
}
```

```js
// v3
plugin(({ addUtilities, matchUtilities, theme }) => {
  addUtilities({ '.scrollbar-none': { 'scrollbar-width': 'none' } });
  matchUtilities({ tab: (v) => ({ tabSize: v }) }, { values: theme('tabSize') });
});
```

`@utility` output sorts inside the `utilities` layer, so `md:`, `hover:`, and `@apply` all work on it; the `*` suffix plus `--value(...)` is what lets it take an argument (`tab-4`, `tab-[7]`).

## Composing Third-Party Components

- Headless kits (Radix, Headless UI, Ark) expose `data-state`, `data-side`, `data-disabled`. Style those with `data-[state=open]:` instead of mirroring state into props.
- A wrapper that forwards `className` and merges with `cn` is the contract; a component that ignores `className` forces the next developer into `!` or a wrapper div.
- `asChild`/slot patterns move the className onto a child element — inspect what actually rendered before concluding the class was dropped.
- Styled third-party components with their own CSS: layer ordering decides, not specificity — runtime-injected styles land unlayered and beat every utility in v4.
- shadcn/ui-style copies-into-your-repo components are just this pattern with the source vendored; edit them freely, and keep `cn` as the merge point.

## Anti-Patterns

| Anti-pattern | Why it hurts |
|---|---|
| `.btn` in `@layer components` with 20 `@apply`s | A private CSS framework with none of Tailwind's constraints and no override path |
| Passing a `color` prop that builds a class (`bg-${color}-500`) | Never scanned; nothing renders (SKILL.md — Class Detection) |
| A `className` prop concatenated with `+` | No conflict resolution; overrides work by luck |
| A component per visual variant (`PrimaryButton`, `DangerButton`) | The variant map exists to prevent exactly this |
| Extracting a component after the second use | Premature: the same `token_threshold` rule (default 3) — the third use is what reveals the real variant axes |
